# 0.6.0 preparation: AI explanation options (decision paper)

Date: 2026-11-14. Nothing has been implemented. This paper prepares the owner's decision on milestone 2.5, opt-in AI explanations.

## Fixed constraints (from CLAUDE.md and the ADRs)

- The tool must work fully with no AI provider. AI is optional and off by default.
- Every AI output is labelled `AiSuggestion`, the weakest evidence class, and is shown next to the deterministic evidence, never instead of it.
- No source code, path or index content leaves the machine without explicit consent per feature. The core crates keep no network code.
- AI must not make claims the evidence does not support. It explains structure Tracemark already found. It does not add calls, findings or verdicts.

## Options

1. **Local Ollama only.**
2. **Bring-your-own API key (BYOK) only**, for a cloud provider such as Anthropic or an OpenAI-compatible service.
3. **Both local and BYOK, disabled by default.**

## Comparison

| Criterion | 1. Ollama only | 2. BYOK only | 3. Both, off by default |
| --- | --- | --- | --- |
| Privacy | Best. Code stays on the machine. | Code snippets go to a third party under that provider's terms. | User's choice. Local is the suggested first choice. |
| Offline | Yes | No | Yes, with local |
| Hardware | Needs a capable machine. Small models (3–8B) run on CPU slowly, and a GPU helps. Model downloads of several GB. | None | None for BYOK users |
| Cost to user | Free after the download; electricity and time | Pay per token to the provider | Either |
| Cost to project | Low | Low | Somewhat higher: two code paths to test |
| Explanation quality | Lower and variable with small models. More risk of confident wrong prose. | Higher with frontier models | Best available to each user |
| Configuration | Install Ollama, pull a model, set an endpoint | Paste an API key, which must be stored securely | Most settings, but the defaults can hide them |
| Provider abstraction | One HTTP client (Ollama also speaks the OpenAI-compatible API) | One or two clients (Anthropic native, OpenAI-compatible) | One small trait with 2 implementations. The OpenAI-compatible client covers Ollama, LM Studio and many hosted services. |
| Data retention | None outside the machine | Governed by the provider's API terms. Tracemark cannot enforce zero retention and must say so. | As per the chosen provider |
| User consent | Still ask once: "AI explanations run a local model" | Must ask per project before the first request, and show what is sent | Per-project consent, naming the provider |
| Labelling | `AiSuggestion` plus the model name | `AiSuggestion` plus provider and model name | Same |

## Rules that apply to every option

- **What is sent:** only the selected symbol's source range, its signature and its evidence-tagged edges. Never the whole repository. String defaults stay redacted. Show the exact payload before the first request ("Preview what will be sent").
- **Where it is shown:** in a separate "AI suggestion" panel, visually distinct, under the deterministic evidence. The panel carries model, provider, time, and the line "Generated by an AI model from the evidence above. It may be wrong. Not verified."
- **Grounding:** the prompt gives only Tracemark's evidence and asks the model to cite `file:line` for every claim. Any claim whose citation does not match a known location is flagged "uncited" in the UI. AI output never changes findings, recommendations or exit codes, and never feeds the MCP review result.
- **Keys:** the OS keychain (Windows Credential Manager, macOS Keychain, Secret Service). Never `.tracemark/`, never logs.
- **Architecture:** a new crate (for example `tracemark-ai`) behind a cargo feature, the only crate with network code. Interfaces call it; `tracemark-index` stays offline. This needs an ADR (new crate, network boundary).
- **Off switch:** no provider configured means no network, verified by a test that the default build has no HTTP client linked.

## Recommendation: option 3, local and BYOK, disabled by default, local first

Reasons:

1. It keeps the product's privacy promise for users who need it (local) without shutting out users whose hardware cannot run a useful model (BYOK).
2. The extra cost is small. One trait and an OpenAI-compatible client cover Ollama and most hosted endpoints. An Anthropic client is the only second path.
3. Ship it in two steps to limit risk:
   - 2.5a: the local Ollama provider, plus the consent, labelling, preview and grounding checks above.
   - 2.5b: BYOK, once the labelling and consent UI is proven.

   Each step is its own PR and milestone.

Why not option 1 alone: small local models produce weaker explanations. A weak explanation next to evidence can mislead beginners, the main audience. Why not option 2 alone: it breaks "nothing is uploaded" as the only path and fails offline.

Owner decisions needed:

- Approve option 3, and the 2.5a/2.5b split.
- Approve a new network-capable crate behind a feature flag (ADR).
- Which BYOK providers to support first.
- Whether AI is offered in the MCP server at all. Recommended: not. Agents already have a model, and MCP results should stay deterministic.
